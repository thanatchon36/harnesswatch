\section{Threat Model and Taxonomy}\label{sec:threats}
\answers{Answers RQ1}

\paragraph*{Adversaries} (A1)~A \emph{content author} controls text the agent reads (a README, comment, issue, web page or tool result); (A2)~a \emph{repository author} controls cloned files, configuration included; (A3)~a \emph{supply-chain attacker} controls a package, MCP server, plugin or release; (A4)~a \emph{local or network peer} reaches a service the harness exposes. The defender runs the harness with real credentials, code and host access (the assets). We assume that the model will sometimes follow injected instructions and that no model-level defence can be relied upon.

\paragraph*{Taxonomy} We extended a sixteen-class seed into the classes of Table~\ref{tab:taxonomy}. Three classes were added because the incident set contained sizeable groups with no natural home: escape from a sandbox or isolation boundary (T17); exposure of the agent's own control plane, typically a local HTTP or WebSocket server without authentication or Origin checks (T18); and conventional software defects in runtimes and SDKs (T19). Each class carries STRIDE letters, MITRE ATLAS techniques, and OWASP LLM~2025, OWASP Agentic (ASI01--ASI10) and OWASP MCP Top~10 identifiers; as the MCP list remains in beta, those mappings are flagged as unstable. Each class also lists its mitigating control dimensions (Section~\ref{sec:controls}) and the \tool{} rules that detect it (Appendix~\ref{app:rules}).

\paragraph*{Classification procedure} Because write-ups conflate the entry vector with the control that failed, we traverse the classes in a fixed order and assign the first whose \emph{failed control} the incident exhibits. A parallel twelve-question procedure assigns one of twelve root causes, RC1--RC12 (Table~\ref{tab:rootcauses}). Thus configuration written by an injection and executed later is T02/RC2 rather than T01, and data leaving through a permitted command is T08/RC3. RC1, untrusted content treated as instructions with no other control failure, is reached only when no earlier question applies; its share is therefore low partly by construction.

\paragraph*{How harness risk differs from LLM-application risk} In a chat application, a successful injection yields a wrong answer or a leaked system prompt. In a harness, the injected text originates in the developer's own workspace and is acted upon with the developer's privileges. Three properties follow. First, \emph{configuration is code}: repository files can define hooks, environment variables and MCP launch commands that execute before the model is consulted (T02). Second, \emph{the approval layer is a parser}: an allowlist over shell commands must reason about quoting, substitution, redirection and symlinks, and failures of this kind form the largest single group of disclosed incidents (T03, \pctTopThree{} by class; RC3, \pctRCThree{} by root cause). Third, \emph{the harness is a long-lived service}: local servers, sub-agents, persistent memory and CI runners create surfaces that classical LLM threat models omit (T10, T11, T18). Attack trees for the principal paths are in the repository.
