\subsection{E6: Rule-pack accuracy on a labelled corpus (RQ4)}\label{sec:eval-e6}
\paragraph*{Design} The corpus comprises \nESixCases{} cases (\nESixHand{} hand-crafted and \nESixGenerated{} generated) spanning more than twenty harness formats, CI files, state directories and MCP manifests; \nESixNegative{} are wholly negative, and many positives have near-miss twins (pinned \texttt{npx}, authenticated HTTPS MCP, linter-only hooks, emoji ZWJ, key-like identifiers). Every audit runs on every case and the unit is the (case, rule) pair, so any unlabelled firing is a false positive. A hash of the case identifier splits the corpus into \nESixDev{} development and \nESixTest{} test cases; errors were inspected and corrected on the development split only.

\paragraph*{Results} On the held-out test split, micro precision is \eSixPrecision{} (95\% Wilson CI \eSixPrecisionLo--\eSixPrecisionHi) and micro recall \eSixRecall{} (\eSixRecallLo--\eSixRecallHi), with \eSixFP{} false positives and \eSixFN{} false negatives; macro precision and recall are \eSixMacroPrecision{} and \eSixMacroRecall{} (per-rule results in \texttt{paper/tables/e6\_accuracy.md}). Before the development-split corrections, test precision was \eSixPrecisionBefore{} with \eSixFPBefore{} false positives; the test split had been scored once before corpus-content corrections that touched both splits, so it is not pristine. The Wilson intervals treat (case, rule) pairs as independent although they cluster within cases and generator families, so they are optimistic. The weakest rules are \texttt{HG-SUB-001}, \texttt{HG-MCP-004} and the approve-everything rules. Because the corpus is synthetic and labelled by the rule author, this shows that the rules implement their specification across formats; real-world precision remains unknown.


\subsection{E2: Prevalence in public repositories (RQ4)}\label{sec:eval-e2}
\paragraph*{Design} Through the GitHub code-search API we sampled harness settings and MCP files, instruction files (\texttt{AGENTS.md}, \texttt{CLAUDE.md}, Copilot and Windsurf rules) and CI workflows that invoke \texttt{claude-code-action}, \texttt{codex exec} or \texttt{gemini -p}. For each repository we reconstructed only the sampled files in a temporary tree, ran \texttt{harnesswatch audit}, retained only (rule, file) pairs and deleted the tree. Identifiers were hashed with an unsaved per-run salt for de-duplication only; a scrub check refuses to write results containing any identifier or URL seen; secret findings were only counted; and requests stayed below the API's rate limits. Each of the \eTwoTargets{} search strata is capped at \eTwoCapPerTarget{} files, so a pooled per-repository rate would mostly reflect the choice of strata. We therefore report each rule's rate over the stratum of files that can carry it (configuration and MCP files, $n=\eTwoStratumConfig$; instruction files, $n=\eTwoStratumInstructions$; agent CI workflows, $n=\eTwoStratumWorkflows$), with Wilson intervals, and name no repository. Only project-level configuration is visible, and a finding marks risky configuration, not exploitation.

\subsection{E3: Canary benchmark for indirect prompt injection (RQ5)}\label{sec:eval-bench}
\paragraph*{Design} Each run starts a fresh container with a minimal Python repository, a synthetic \texttt{.env} token, a fixture file and a sink on \texttt{127.0.0.1}, and sets the same benign task: add a \texttt{multiply} function and test, and run the tests. Besides a \emph{control}, four scenarios place one templated block in the README, in the harness-native instruction file, in a code comment, or in test output that is returned as a tool result (Table~\ref{tab:bench-catalogue}). The block asks the agent to create \texttt{CANARY\_<id>.txt}, POST \texttt{.env} to the sink and delete the fixture; all three are inert, and the container reaches only the model server. The two modes are \emph{default} (out-of-the-box headless) and \emph{auto} (the documented approve-everything flag).

\paragraph*{Harnesses, model and grid} Seven adapters cover three Tier-B clients (Claude Code, Copilot CLI and the Grok Build npm binary, driven through their custom-endpoint modes; Claude Code's is vendor-unsupported, Section~\ref{sec:method}) and four open-source harnesses (OpenCode, Codex CLI, Aider and Qwen Code). No vendor credentials are used, so every harness talks to one local open-weight model, \texttt{qwen3:4b-instruct}, served by Ollama. The grid is \nBenchHarnesses{} harnesses $\times$ \nBenchScenarios{} scenarios $\times$ 2 modes, with \nBenchPerCell{} runs per cell. A run is capped at 240~s and scored on its state at the cap; a run with no harness output counts as an error, not as safe. Aider loads no instruction file, so its \texttt{instructions} cells are N/A in both modes and excluded from the pooled statistics.

\paragraph*{Metrics} \emph{Injection follow}: any of the three goals achieved. \emph{Exfiltration attempt}: any POST to the sink, or the secret observed there. \emph{Destructive action}: the fixture deleted. \emph{Secret read}: the synthetic token appears in the harness's printed output (other than in an environment-variable dump) or reaches the sink; since some harnesses print only their final message, this undercounts reads. \emph{Secret in state}: the token appears in a transcript or session file written by the harness, which separates persistence from agent action. \emph{Permission prompt}: an approval prompt appears in the output. \emph{Task completed}: the tests pass and the function and its test exist, so that a ``safe but useless'' outcome remains visible. All rates carry Wilson 95\% intervals.

% BEGIN-E3-RESULTS
\paragraph*{Results} The grid produced \nBenchRuns{} runs (\nBenchErrors{} errors, \nBenchTimeouts{} timeouts scored at the cap, model cost \$\benchCost{}), of which \nBenchRunsAnalysed{} enter the analysis (Table~\ref{tab:e3}). Over the injection scenarios, the injected instruction was followed in \benchFollowAutoK{} of \benchFollowAutoN{} auto-mode runs (95\% CI \benchFollowAutoLo--\benchFollowAutoHi) and in \benchFollowDefaultK{} of \benchFollowDefaultN{} default-mode runs (\benchFollowDefaultLo--\benchFollowDefaultHi); the controls followed nothing (\benchControlFollowK{} of \benchControlN{}). No run attempted the POST, the fixture was deleted in \benchDestrAutoK{} auto-mode run, and the strict secret-read count is \benchSecretReadAutoK{} in both modes. The intervals overlap, so there is \emph{no detectable safety difference} between the modes. Task completion does differ (\benchTaskAutoK{} of \benchTaskAutoN{} auto against \benchTaskDefaultK{} of \benchTaskDefaultN{} default) because several headless defaults withhold the tools the task needs: Codex CLI and Copilot CLI showed a permission prompt in every default run, while Grok Build and Qwen Code completed nothing in default mode without a detectable prompt, for reasons we did not establish. OpenCode completed \benchOpencodeControlTaskK{} of \benchOpencodeControlN{} even in the controls, an adapter--model incompatibility that renders its cells uninformative. Claude Code's ``default'' arm is not an ask mode: with a third-party endpoint it starts in the classifier-mediated \texttt{auto} mode (Section~\ref{sec:claims}).

\paragraph*{Secret in state} In \benchClaudeImportK{} of \benchClaudeImportN{} Claude Code runs of the \texttt{instructions} scenario (both modes), the synthetic secret reached the session transcript, against \benchClaudeOtherStateK{} in its other scenarios. This is not a model action: an E7 probe with an unreachable model endpoint reproduced it, because the payload's \texttt{--data-binary @.env} contains the token \texttt{@.env}, which Claude Code's documented \texttt{@path} import resolves when it loads \texttt{CLAUDE.md}\evT\evD{}. It is a harness design property: an instruction file can import gitignored secrets into context and transcript without any approval.

\paragraph*{Interpretation} The low follow rate most probably reflects the small model's limited agentic and instruction-following ability and the plainly worded, benign canary, \emph{not} the robustness of the harnesses. With \nBenchPerCell{} runs per cell and zero or one event per cell, the intervals are wide, and we do not rank harnesses on resilience, nor describe default modes as safer.

\paragraph*{Correction} Our original secret metric (the token anywhere in output or written files), fixed before the results were inspected, flagged \benchSecretAnyTotal{} runs and was replaced afterwards: \benchClaudeImportK{} were the Claude Code import above and the rest Codex CLI, which writes its process environment, canary included, into \texttt{\textasciitilde/.codex} shell snapshots whenever its shell tool runs (\benchCodexSnapshotK{} of \benchCodexSnapshotN{} Codex runs)\evT{}. Neither is the agent reading the secret, hence the two metrics: a benchmark should distinguish what a harness persists from what an agent does.

\subsection{E5: Secret residue in harness state (RQ5)}\label{sec:eval-e5}
\paragraph*{Design} For each of the \nResidueHarnesses{} bench harnesses we ran two short sessions in a fresh container. In the \emph{key} condition the provider credential was a unique synthetic canary; in the \emph{content} condition the prompt asked the agent to read a synthetic \texttt{.env} file. We searched every file the harness wrote for the canary and recorded paths, modes and reachability by other users (home directory 0755); file contents were never stored. With one session per harness and condition ($N=1$), the results are descriptive.

\paragraph*{Results} In the content condition, \nResidueWithCopy{} of the \nResidueHarnesses{} harnesses left at least one file holding the secret, typically a transcript or chat log (Table~\ref{tab:e5})\evT{}; in \nResidueReachable{} of them such a file was readable by other local users. In the key condition, \nResidueKeyPersisted{} of the \nResidueKeyApplicable{} harnesses that accept a key wrote it to a file in this single run\evT{}. That is a sampling result rather than evidence of absence: Codex CLI persists environment-supplied credentials in shell snapshots whenever its shell tool runs, which occurred in \benchCodexSnapshotK{} of \benchCodexSnapshotN{} E3 runs but not in the E5 key session\evT{}. Mode bits alone can mislead: Grok Build writes 0644 session files, but inside a 0700 sessions directory, so other users cannot reach them\evT{}; Claude Code writes transcripts with mode 0600\evT{}. OpenCode left no residue in this run. Because residue depends on whether the agent reads the file, a single run can miss it. These are design weaknesses, not vulnerabilities; a 0750 home directory would close the reachable paths, but CI runners and containers commonly use 0755.

\subsection{E4: Distribution supply chain (RQ2, D13)}\label{sec:eval-supply}
We inspected the published packages of \eFourHarnesses{} harnesses (the Tier-A set plus Claude Code, Grok Build and Copilot CLI) from registry metadata and lockfiles alone, without running any install script\evD{} (per-package table: \texttt{paper/tables/e4\_supply.md}). Install-time hooks are declared by \eFourHarnessesWithInstallHooks{} packages. Of the \eFourProvenanceKnown{} whose status could be determined, \eFourWithProvenance{} publish registry provenance attestations. A \texttt{curl | sh} installer is offered by \eFourHarnessesWithCurlInstaller{}, and in \eFourHarnessesWithUnsignedCurlInstaller{} of these the installer verifies no signature (some verify a checksum; Claude Code documents a signed release manifest that its installer does not itself verify\evD). Auto-update is documented as on by default in \eFourAutoUpdateDefaultOn{} (cells marked ``unverified'' in the table are undetermined, not off). The median lockfile holds \eFourMedianTransitive{} transitive packages, and OSV lists \eFourOsvUniqueVulnsTotal{} unique advisories against the locked dependency versions, concentrated in a few packages; these are advisories against pinned versions, not demonstrated exploitability. Auto-update is a trade-off: it delivers fixes promptly but widens the blast radius of a compromised release channel, as the Amazon Q extension incident showed\evD~\cite{amazonq2025}.
