\section{Introduction}\label{sec:intro}
\answers{Motivates RQ1--RQ7 and summarises the contributions}

In 2025 and 2026, coding agents left the chat window for the terminal, the IDE and the CI pipeline, and vendors and open-source projects converged on one architecture: an agent is a \emph{model} plus a \emph{harness}. The harness is the program around the model: it assembles context from the repository, exposes tools (shell, file editing, web fetch, MCP servers), decides which tool calls require human approval, stores credentials and transcripts, spawns sub-agents, and can run unattended in CI. The model proposes; the harness executes.

Most security research on LLM agents addresses the model, asking whether it follows injected instructions~\cite{greshake2023,agentdojo,injecagent}, with the tool-execution layer held fixed. Yet the harness decides whether an injected instruction becomes a shell command, whether a cloned repository can run a hook before the user has consented, whether an MCP server starts from a cloned file, and whether a secret lands in a world-readable log. These are deterministic software decisions, and they can be specified, tested and audited like any other access-control code.

The public record points the same way. Of the \nIncCounted{} verified harness-level advisories and incidents we collected for 2025--2026 (Section~\ref{sec:incidents}), \nIncRCThree{} arise from flawed approval, allowlist or path checks and \nIncRCTwo{} from workspace configuration honoured before consent; only \nIncRCOne{} are pure prompt injection. Since model failures seldom receive CVEs and RC1 is the residual class of our procedure, these shares describe disclosed harness bugs rather than overall risk; within that scope, injection is often the vector, but harness controls decide the damage.

Comparing harnesses is difficult: the field changes monthly, many popular harnesses are closed source, and documentation describes intended rather than actual behaviour. We therefore organise the study by \emph{method}: white-box analysis for open source, black-box observation for closed harnesses that we can run, documentation for those we cannot, and a separate track for SDK runtimes (Section~\ref{sec:method}).

\paragraph*{Research questions}
\RQ{RQ1}: What is the attack surface of a harness, and how does it differ from classical LLM-application risk?
\RQ{RQ2}: How do harnesses differ in the security controls they provide?
\RQ{RQ3}: Which harness-level incidents were disclosed in 2025--2026, and from which root causes?
\RQ{RQ4}: Can dangerous configuration be detected automatically across harness formats?
\RQ{RQ5}: How resilient are harness $\times$ model $\times$ permission-mode combinations to indirect prompt injection and secret residue, as measured with inert canaries?
\RQ{RQ6}: Which controls should an organisation mandate before adopting a harness?
\RQ{RQ7}: For closed harnesses, do the documented controls match the observable behaviour of the client?

\paragraph*{Contributions} A harness threat taxonomy with framework mappings (RQ1, Section~\ref{sec:threats}); an evidence-linked control matrix of \nHarnesses{} harnesses and runtimes (RQ2, Section~\ref{sec:controls}); a black-box claims-versus-observed method for closed harnesses (RQ7, Section~\ref{sec:claims}); a two-source incident survey (RQ3, Section~\ref{sec:incidents}); \tool{}, an Apache-2.0 auditor, with accuracy, prevalence, canary-bench and residue experiments (RQ4, RQ5, Sections~\ref{sec:tool}--\ref{sec:eval}); and a governance checklist (RQ6, Section~\ref{sec:governance}). \texttt{make all} rebuilds every table, figure and reported number from versioned results (Appendix~\ref{app:repro}).
